# Противоречия и актуализация

`features/conflicts/` · приоритет **P1** · закрывает: задача 3, доп.: актуализация

## Зачем (что видит пользователь)
Видит «мнения расходятся» и предупреждения «рядом стройка в ваши даты».

## Бэкенд / пайплайн → `backend/`, `pipeline/`
Verifier: находит несовместимые факты из разных источников → статус conflict → вопрос отельеру. Перепроверка фактов с истёкшим сроком, «Пульс места».

## Фронт → `frontend/`
Плашка «мнения расходятся», лента изменений.

## API
`GET /api/hotels/{id}/pulse`

## Зависит от
facts, hotelier

## Готово, когда
- [ ] Данные/расчёт работают на демо-данных Сочи и лежат в `data/` (или воспроизводятся скриптом)
- [ ] Факты пишутся в хранилище с источником, уверенностью и датой (если фича производит факты)
- [ ] API отвечает по контракту выше, есть пример запроса/ответа в этом README
- [ ] Фронт показывает результат в стиле Островка (wiki/design-system.md)
- [ ] Работает без ключа LLM (fallback)

## Статус и заметки
- Статус: **v0 работает** (26.10, Claude) — противоречия «ответ отеля ↔ расчёт». Актуализация и «Пульс места» — бриф 6 в `wiki/roadmap.md`.
- **Правила** (`backend/compare.py`, без LLM): `sea_view` — «из всех номеров» / «нет вида» / «с N-го этажа» против видимости по сторонам; `beach` — минуты отеля против пешего маршрута (разница ≥5 мин и ≥1,8 раза); `floors` — этажность отеля против OSM (разница ≥2). Новое правило — функция в `RULES`.
- **Где срабатывает**: `knowledge.resolve()` — у ответа отеля появляется `conflict {hotel_text, computed_text, reason, status: open|explained, explanation}`; пока `open` — заметка «Мнения расходятся — уточняем у отеля», уверенность = минимум из двух.
- **Гость** (`frontend/ConflictNote.jsx`): в «Частых вопросах» — обе версии; в «Что важно знать» — короткое «Отель пишет иначе». После пояснения — «Отель пояснил: …».
- **Отельер** (`frontend/ConflictsPanel.jsx` в Экстранете): «Расчёт верный — поправить мой ответ» (ответ отеля = расчёт) или «Мой ответ верный — объяснить» (пояснение в evidence; гость видит версию отеля и пояснение). История — в базе знаний (superseded).
- **Демо**: Pullman — «вид на море из всех номеров» (так отель пишет о себе), «Альбатрос» — «до моря 5 минут» при маршруте 18 мин и 96 м в гору (`features/hotelier/demo_answers.json`).
- API: `GET /api/hotels/{id}/conflicts` → `[{topic, question, icon, hotel_text, computed_text, computed_source, computed_confidence, reason, status, explanation}]`; `POST /api/hotelier/{id}/conflicts/{topic} {"action": "adopt"}` | `{"action": "explain", "text": "..."}`.
- **Сайт отеля ↔ расчёт** (26.10, `check_site`, `site_conflict(hotel_id, topic, computed)`): обещания с сайта (`web:sea_view`, `web:beach_claim` из `features/web_sources`) сверяются теми же правилами. Минуты («10 минут до пляжа») — против пешего маршрута; метры и «первая линия» — против расстояния **по прямой** (`beach_distance`; разница ≥250 м и ≥1,5 раза, «первая линия» дальше 350 м), иначе «10 м от пляжа» у «Кавказа» (14 м по прямой, 7 мин маршрутом через вход) было бы ложным расхождением. Подключено в `knowledge.resolve()` на уровне расчёта: у ответа `conflict.kind = "site"`, заметка «Отель пишет иначе — уточняем», уверенность ≤0,6.
  - Гость: «Отель пишет иначе» в «Что важно знать», «Мнения расходятся: Сайт отеля / Наш расчёт» + ссылка на страницу в «Частых вопросах».
  - Отельер: та же панель, «На вашем сайте» + кнопки «Расчёт верный — показывать гостям его» / «На сайте верно — объяснить». Своего ответа у отеля ещё нет — разбор и становится ответом отеля (текст сайта + пояснение).
  - **Метрика: нашли 9 расхождений сайта с расчётом** (8 — пляж, 1 — вид из окна; список в `features/web_sources/README.md`) + 1 демо «ответ отеля ↔ расчёт» (Pullman); закрыто — 0 (закрывает отельер в Экстранете; проверено на тестовой базе: пояснение → `explained`, принятие расчёта → расхождение пропадает).
- Исправлено: после «Расчёт верный» в value ответа оставалось прежнее значение («все номера», «5 минут»), и расхождение находилось снова; теперь ответ с `evidence.action = adopted_computed` не сверяется.
