# Итоговое решение: чек-лист сдачи (29.10 до 10:00 МСК)

Три слоя: **(A)** без этого решение не примут/не оценят; **(B)** обязательное содержание по треку; **(C)** то, чем выигрываем. Подробности фич — [product-concept](product-concept.md), требования — [requirements](requirements.md).

## A. Формальная сдача (из правил по технике)
- [ ] Код в репозитории команды в `ostrovok-hackathon-2026`, git-тег `submission` на последнем коммите основной ветки
- [ ] `git clone` → `cp .env.example .env` → `docker compose up --build` → http://localhost:8080, ≤10 мин, без ручных шагов
- [ ] `Dockerfile` (multi-stage, не root, `linux/amd64`), `docker-compose.yml` (8080:8080, healthcheck, env_file), `/health` → `{"status":"ok"}`
- [ ] `.env.example` (ключ LLM, модель, URL — с описанием; без ключа всё работает в упрощённом режиме)
- [ ] `README.md` по шаблону: что делает · ссылка на видео · быстрый старт · ресурсы и переменные · данные/сидирование · маршруты
- [ ] **Видео-скринкаст** 2–3 мин, открывается в инкогнито
- [ ] Демо-данные в репозитории + описание, **как они получены** (и скрипт, который это воспроизводит)
- [ ] (опц.) ссылка на развёрнутый сервис, Makefile

## B. Обязательный результат трека
«Работающий прототип для набора отелей выбранного региона, в котором пользователь может найти отель по собранным системой характеристикам».
- [ ] Набор реальных отелей Сочи (из OSM; базовые поля карточки — мок)
- [ ] Характеристики, которых нет в карточке, **собранные системой**; минимум одна — **вычислена по геоданным** (вид на море / путь до пляжа с подъёмом)
- [ ] У каждого значения: источник, уверенность, дата
- [ ] Пользователь **находит отель** по этим характеристикам

## C. Что делает решение сильным
**Ответ на три вопроса эксперта** (обязательная «подача», хоть и не чек-лист):
- [ ] Важно ли ему → «главное — первым» под контекст поездки
- [ ] Можно ли доверять → доказательства, «мнения расходятся», калибровка уверенности
- [ ] Повлияет ли на решение → режим «было / стало»

**Опорные задачи трека** (закрываем все — это то, что жюри ожидает увидеть):
- [ ] Агенты сами выбирают источник/инструмент под характеристику
- [ ] Вопрос отельеру → свободный ответ → поля (отельер имитирован)
- [ ] Противоречия источников замечаются и разбираются
- [ ] Новая характеристика добавляется описанием, без переписывания кода
- [ ] Поиск по своим словам («✨ опиши» → линзы)

**Наши киллер-фичи (в порядке ценности для демо):**
1. [ ] 3D-карта с линзами и ползунком времени
2. [ ] «О!кно» — вид из номера + выбор окна на фасаде + пожелание к брони
3. [ ] «Твой день здесь»
4. [ ] «Было / стало»
5. [ ] Кабинет отельера с «упущенными гостями»
6. [ ] Сравнение / отпечаток, «Пульс места», «Так и было?» — если успеем

**Метрики в README** (маленькая своя разметка 20–40 отелей):
- [ ] точность вида на море и времени до пляжа, калибровка уверенности
- [ ] покрытие (доля отелей с надёжными фактами), доля вопросов к отельеру
- [ ] доля запросов, где наши факты меняют топ-3

## Чего в решении быть НЕ должно
- Фактов, которые придумала нейросеть («LLM угадала вид на море»)
- Чат-бота как главного интерфейса
- Зависимости от платного ключа для базовой работы
- Многочасовой загрузки данных при запуске
