# План доработок до сдачи (29.10, 10:00 МСК)

Каждый раздел «Бриф» ниже — **самодостаточное задание для отдельного агента**: копируете раздел целиком в новый чат. Перед любым брифом агент читает `AGENTS.md`, `wiki/index.md`, `wiki/architecture.md`, `wiki/design-system.md`.

## Общие правила для всех агентов (вставлять в начало каждого чата)
1. **Своя ветка**: `feat/<папка>-<кратко>` от свежего `main`. В `main` — только после проверки в браузере, перед мержем `git pull --rebase origin main`.
2. **Своя папка**: весь код фичи — в `features/<папка>/` (backend, pipeline, frontend, свой `<папка>.css`, импортируемый из компонента). **В общие файлы — минимум**: одна строка подключения роутера в `app/main.py`, одна строка монтирования компонента в `HotelCard.jsx` / `SearchPanel.jsx` / `App.jsx`. В `app/frontend/styles.css` не писать.
3. **Факты** — только через `data/seed/facts_<папка>.json` или `register_provider` (`features/facts/backend`), модель — `wiki/architecture.md`: источник, уверенность из качества данных, дата, срок годности.
4. **LLM не придумывает факты.** LLM может: понять запрос, выбрать инструмент, извлечь факт из текста **с дословной цитатой и ссылкой** (это источник, а не догадка), перефразировать. **Всё работает без ключа** (правила/предсохранённое), с ключом — лучше.
5. **Стиль Островка**, без разделителей «·», без техтекста в интерфейсе, без легенд-загадок (`wiki/design-system.md`).
6. **Сборка ≤10 мин.** Тяжёлое — заранее в `pipeline/`, результат в `data/seed/` (в git), сырьё в `data/raw/` (не в git) + скрипт скачивания. Новые Python-зависимости рантайма — только лёгкие и с фиксированной версией в `app/requirements.txt`.
7. **Проверка**: `sh tools/dev_check.sh` (или свой порт `PORT=809x`), открыть в браузере, проверить на 2–3 отелях (Pullman `#w201474333`, Azimut `#w51764141`, «Чайка» `#w711599965`). Отчёт — в `features/<папка>/README.md` «Статус и заметки» + строка в `wiki/inbox.md`.

## Бриф 1. Агент-исследователь и реестр инструментов (`features/characteristics/`)
**Зачем.** Задание — «прототип **агентной** системы»; задачи 1 и 4: «агент сам решает, какие источники и инструменты нужны», «новую характеристику можно добавить, описав текстом». Сейчас у нас хорошие, но жёсткие скрипты.

**Как устроено.**
1. **Реестр инструментов** `features/characteristics/backend/tools.py` — обёртки над тем, что уже есть, с описанием на русском (для LLM и для показа гостю):
   - `viewshed` — вид из окна (данные `features/okno`), `walk_route` — пеший путь (`core/walk.py`), `poi_nearby` — ближайший объект OSM нужного типа (`features/nearby`), `noise_model` (`features/noise`), `climate` (бриф 4), `web_text` — поиск по сайту отеля (бриф 2), `ask_hotelier` — вопрос в очередь (`features/hotelier`).
   - Каждый инструмент: `run(hotel_id, params) -> {value, confidence, evidence, source}`.
2. **Спецификации характеристик** `features/characteristics/specs/*.yaml` (перенести/обернуть существующие: sea_view, sunset_view, beach_route, noise, 36 «рядом»): `id, title, question, value_type, plan: [шаги с инструментами по порядку], min_confidence, ttl_days, ask_hotelier: "текст вопроса"`.
3. **Планировщик** `planner.py`: для (отель × характеристика) идёт по `plan`: шаг → если уверенность ≥ порога, стоп; иначе следующий инструмент; в конце — `ask_hotelier`. Каждое решение пишет в **трассу**: «попробовал `web_text` — не нашёл; `poi_nearby` — велодорожка в 240 м, уверенность 0,8».
4. **«Описать текстом»** `POST /api/characteristics/from-text {text}`:
   - без ключа: `core/textmatch` + шаблоны («рядом/в N метрах + объект» → `poi_nearby` с тегами OSM из словаря; «есть ли в номере/отеле…» → `web_text`, затем `ask_hotelier`);
   - с ключом: LLM получает реестр инструментов и возвращает YAML-спеку; спека валидируется по схеме, показывается на подтверждение.
   - после подтверждения планировщик прогоняет характеристику по всем отелям (асинхронно, прогресс в API) → факты появляются в поиске и карточках.
5. **В интерфейсе.** Аккуратно: в карточке у каждого факта в «как узнали» — короткая трасса агента («Проверили сайт отеля → нашли на карте → уверенность высокая»). Экран «Добавить характеристику» — в разделе «Для отелей» (Экстранет) или скрытый `/#/admin`: поле текста → предпросмотр спеки по-человечески → «Посчитать для всех отелей» → прогресс.
**API.** `GET /api/characteristics`, `POST /api/characteristics/from-text`, `POST /api/characteristics/{id}/run`, `GET /api/characteristics/{id}/status`, `GET /api/facts/{id}/trace`.
**Готово, когда.** Текст «есть ли рядом велодорожки» без ключа превращается в спеку `poi_nearby(cycleway)`, считается по 718 отелям <1 мин, появляется линзой в «Ещё фильтры» и строкой в карточке с трассой. С ключом — то же для произвольной формулировки. Сценарий для видео записан в README.

## Бриф 2. RAG по сайтам отелей (`features/web_sources/`)
**Зачем.** Многое знает только отель: шторы блэкаут, шумоизоляция, питомцы, детская кроватка, парковка. Это и есть «LLM + RAG» поверх открытых данных — но **факт = цитата из источника**, а не догадка.
**Источники.**
- **Официальные сайты:** у **236 из 718** объектов есть `website` в OSM. Это публичная информация самого отеля — используем.
- **Отзывы:** скрапинг агрегаторов (Островок, Яндекс, Tripadvisor) — **не делаем** без разрешения (условия сайтов; вопрос участников про выгрузки отзывов организаторы оставили без ответа). Задать на Q&A 27.10. Если разрешат открытые исследовательские датасеты — подключаем тем же конвейером.
**Как.**
1. `pipeline/crawl.py`: для каждого сайта — главная + до 10 страниц того же домена с ключевыми словами в URL/ссылке (номера, услуги, правила, faq, о-нас, контакты, животные, парковка). Уважать `robots.txt`, 1 запрос/сек на домен, таймаут, User-Agent проекта. Сохранить текст (`trafilatura` или `readability-lxml` — только в pipeline, не в рантайме) → `data/raw/web/<hotel_id>/*.json` {url, title, text, fetched_at}.
2. `pipeline/index.py`: чанки по ~600 символов с перекрытием → `data/seed/web_chunks.json` (только чанки, без HTML). Индекс **BM25 с леммами** (`core/textmatch`, pymorphy3) — работает без ключа. С ключом и если успеем — эмбеддинги через OpenAI-совместимый API, предпосчитанные в seed.
3. `pipeline/extract.py`: для списка тем базы знаний (`features/knowledge`: шторы, шумоизоляция, питомцы, дети, парковка, кухня, кондиционер, трансфер…) — найти чанки → без ключа: правила/регулярки («блэкаут», «животные не допускаются», «до 10 кг»); с ключом: LLM извлекает `{value, quote}` **строго из чанка**, иначе «нет ответа». Проверка: цитата должна дословно встречаться в чанке, иначе факт отбрасывается.
4. Факты: `source: "web:<домен>"`, `evidence: {url, quote, fetched_at}`, уверенность 0,7 (прямая формулировка) / 0,5 (косвенная), срок годности 90 дней.
5. Инструмент `web_text` для брифа 1: `search(hotel_id, question) -> top chunks`.
**В интерфейсе.** Не отдельный блок: факты встают в «Что важно знать» и в ответы «Частые вопросы» с подписью «с сайта отеля» и цитатой по клику (ссылка на страницу). В «опиши» — вопрос, на который есть ответ на сайте, отвечается сразу, а не уходит отельеру.
**Готово, когда.** Обойдены все 236 сайтов (или сколько отвечают — записать долю), ≥10 тем, факты с цитатами у ≥100 отелей; пример на видео: «можно с собакой?» → «Да, до 10 кг — с сайта отеля» + цитата.

## Бриф 3. Противоречия источников (`features/conflicts/`)
**Обязательно ли?** «Основные задачи» — опорные, не обязательные; но задача 3 прямо говорит «если источники противоречат, система замечает и разбирается», и это лучший ответ эксперту на «можно ли доверять». Делаем.
**Учесть решение 25.10:** поправка отельера главнее расчёта, спор «отель против расчёта» гостю не показываем.
**Как.**
1. `pipeline/detect.py`: попарно сравнить факты одной характеристики из разных источников: расчёт видимости ↔ сайт («все номера с видом на море»), карта шума ↔ сайт/отзывы («тихий район»), OSM `stars` ↔ сайт, «до пляжа N мин» ↔ сайт («5 минут до моря»). Правила сравнения — в спеке характеристики (бриф 1) или в `rules.yaml`.
2. Исход: `conflict` → (а) вопрос отельеру в очередь Экстранета с обеими версиями и доказательствами («Сайт: „вид на море из всех номеров“. Расчёт: с 1–3 этажа северной стороны моря не видно. Уточните?»); (б) уверенность обоих фактов снижается до ответа; (в) после ответа отельера — его версия главная, расхождение закрыто, в истории остаётся.
3. Гостю — только мягко: у факта слово «уточняем» вместо «по расчёту».
**Готово, когда.** Найдены расхождения у ≥5 реальных отелей (Pullman — первым), они видны в Экстранете с доказательствами, после ответа отельера факт обновляется. Строка метрики в README: «нашли N расхождений, M закрыто».

## Бриф 4. Погода, вода, воздух (`features/climate/`)
**Данные.** Open-Meteo без ключа: Archive API (температура воздуха, осадки, солнечные часы, 2015–2025) и Marine API (температура воды) — для 3–4 точек побережья (Мамайка, Центр, Хоста, Адлер; отель берёт ближайшую). Air Quality API Open-Meteo (PM2.5) по месяцам. Скачать один раз → `data/seed/climate.json` (килобайты).
**Факты/API.** Не факт отеля, а факт места и месяца: `GET /api/climate?lat&lon&month` → `{air_day, air_night, water, rain_days, sunny_hours, pm25, text}`. Тексты по-человечески: «Вода 17° — бодрит», «в октябре ещё купаются (вода 20°)».
**В интерфейсе — аккуратно.** (1) В плашке поездки в шапке при выборе дат — маленький значок «☀ 24° · вода 18°»… *без «·»*: два коротких чипа. (2) Строкой в «Твой день» (бриф 7). (3) Никаких отдельных экранов.
**Готово, когда.** Данные за 10 лет по месяцам для 4 точек, API, отображение в шапке; проверено: май — вода ~17°, август ~26°.

Варианты: (а) «Ласточка» Аэропорт → Сочи/Хоста/Мацеста/Адлер — расписание с сайта РЖД/ЦППК вручную в `data/seed/airport_schedule.json` с датой и ссылкой (честно: «расписание на 26.10»); (б) автобусы 105/105с/124с/135 — маршруты из OSM (`route=bus`), интервал вручную с сайта перевозчика; (в) такси — время по нашему графу дорог или по прямой ×1,4 / 40 км/ч, цена — «ориентир» с пометкой.

**В интерфейсе.** Одна строка в карточке «Из аэропорта: 42 мин на „Ласточке“ без пересадок, ночью — такси» и первая сцена «Твоего дня» (прилёт), если рейс ночной.

## Бриф 6. Связь, «Пульс места», история здания, фото (`features/place_context/`)
Четыре маленьких источника, **каждый — одна аккуратная строка в карточке, не отдельный экран**.
1. **Связь для удалёнки.** OpenCellID (нужен бесплатный токен — у пользователя) или Mozilla Location Service-дамп; вышки LTE/5G в радиусе 1 км → «Хорошая мобильная связь 4G, 5G рядом есть». Нет токена → не делаем строку, без заглушек. Плюс линза «Удалёнка» = связь + тишина днём + кафе (`nearby`).
2. **«Пульс места».** Стройки: OSM `landuse=construction`, `building=construction` в 300 м → «Рядом стройка (OpenStreetMap, на 26.10)». Мероприятия: 5–10 крупных событий Сочи на даты поездки вручную из открытых афиш с ссылкой (фестиваль «Кинотавр» — июнь, набережная) в `events.json` с геозоной → плашка в карточке «12–14 мая на набережной фестиваль — до 23:00 шумно». Пересчёт тишины (бриф `noise`) в эти даты — если успеем.
3. **История здания.** Wikidata/Википедия по `wikidata` тегу (их всего 3) + поиск по названию/координатам в Wikidata (`P625` в 100 м) → «Здание санатория 1936 года, памятник архитектуры». Только если нашлось — строка «О здании».
4. **Фото с геометками.** Wikimedia Commons API (`geosearch` 150 м) и Mapillary (токен — у пользователя) → полоска из 3–6 фото «Вид с улицы» с автором и лицензией. Без фото — блока нет.
**Готово, когда.** Каждая строка появляется только при наличии данных, с источником и датой; на 3 отелях показано. Токены — в `.env.example` с пояснением, без них сервис работает.

## Бриф 7. «Твой день здесь» (`features/day/`)
**Что.** Лента одного дня в выбранные даты для выбранной стороны/этажа, собранная **только из готовых фактов** — история вместо таблицы, с честными подвохами.
**Сцены (показывать только те, для которых есть факт):**
- прилёт (бриф 5, если поздний рейс), утро: солнце в окне / не разбудит (восход по профилю «О!кна», сторона восток);
- пляж: время вниз (`beach_route`), вода в эти даты (бриф 4);
- обратно: время вверх и подъём («с коляской тяжело», если режим «с ребёнком»);
- вечер: закат из окна (время из `okno`, «закроет дом в 18:39» — честно);
- ночь: шум по стороне (`noise`), бар до 02:00 (`nearby` `opening_hours`), круглосуточная аптека.
**Как.** `backend/day.py`: `GET /api/hotels/{id}/day?month&facade&floor` → список сцен `{time, icon, title, note, good: bool, fact_ids}`; время сцен — из фактов (закат, восход) или шаблона (09:00, 13:00, 23:00). Каждая сцена кликается → «как узнали» факта.
**В интерфейсе.** Блок в карточке после «О!кна», вертикальная лента в стиле Островка, хорошие сцены — обычные, подвохи — мягкий оранжевый (`--warn-bg`), синхронизирован с выбранными стороной/этажом в «О!кне».
**Готово, когда.** У Pullman, Azimut, «Чайки» день отличается по смыслу; сцен без данных нет; на видео — 15 секунд.

## Бриф 8. Фасад: выбрать окно + пожелание к брони (`features/facade/`, `features/booking/`)
**Что.** Развёртка/схема здания: этажи × стороны, клетки окрашены «море / закат / тихо / шумно / закрыто». Клик по клетке = выбор стороны и этажа в «О!кне». Итог — **рекомендация к брони**: «Просите западную сторону, 8+ этаж, подальше от бара».
**Как.** Данные уже есть: `okno` (доля моря по каждому этажу), `noise` (по сторонам), закат. `facade/frontend/FacadeGrid.jsx`: колонки — стороны, строки — этажи сверху вниз, клетка = цвет главного свойства + маленькие значки; легенда — словами под сеткой одной строкой. Рекомендация — `GET /api/hotels/{id}/request?wishes=sea_view,quiet` → `{text, facade, min_floor, reasons[]}`.
**Бронь (мок).** `booking/frontend/BookBox.jsx` в карточке: цена + «Забронировать с пожеланием» → экран-подтверждение с пожеланием, которое «уходит отелю» (в Экстранете у отеля появляется заявка с пожеланием; отель может ответить «подтверждаем / не сможем»). Сохраняем бронь в памяти/`data/runtime/` → нужно брифу 11.
**Готово, когда.** На Pullman: клик «запад, 16» → «О!кно» переключается, рекомендация «запад, 8+», бронь с пожеланием видна в Экстранете.

## Бриф 9. 3D-вид из окна (`features/okno/frontend/view3d/`)
**Что.** Сцена от первого лица из выбранного окна: рельеф, дома, море, небо и солнце в выбранный месяц/час. Ползунок времени суток (закат «садится» в море или за дом).
**Стек.** three.js (cdn или npm, фикс. версия) — свой рендер, без внешних тайлов рельефа: работает офлайн у жюри.
**Данные (pipeline, заранее).**
1. `pipeline/export_terrain.py`: один **региональный heightmap** Сочи из Copernicus (bbox побережья ~40×30 км, шаг 30 м → ~1300×1000 int16 ≈ 2,6 МБ, бинарь) + метаданные; море = 0.
2. `pipeline/export_buildings3d.py`: для каждого отеля — дома в 700 м: контуры (упрощённые, в метрах от окна) + высота + земля → `data/seed/okno3d/<id>.bin|json` (~50–100 КБ), всего ≤15 МБ; или общие тайлы на все отели.
**Рендер.** Плоскость рельефа (вблизи 2 км — подробно, дальше — грубее), море — плоскость с лёгким материалом, дома — `ExtrudeGeometry`, камера в точке окна (`eye` из API «О!кна») на высоте этажа, направление — нормаль фасада, FOV 70°; солнце — `DirectionalLight` + диск по азимуту/высоте из suncalc (в браузере) на 15-е число месяца; небо — градиент. Подсказка-оверлей: «Солнце сядет в море в 20:03» из уже посчитанного `sun`.
**В интерфейсе.** В блоке «О!кно» кнопка «Посмотреть из окна» → окно-модалка/полноширинный блок 16:9; переключатели стороны/этажа общие с «О!кном».
**Готово, когда.** Для Pullman (запад, 16 — море и закат; запад, 1 — дом слева) и Azimut картинка узнаваемо совпадает с расчётом; FPS ок на ноутбуке; размер данных ≤20 МБ.

## Бриф 10. Сравнение, отпечаток, «Было / стало» (`features/compare/`)
1. **Отпечаток отеля** — круглый глиф из 6–8 лепестков (море, закат, пляж, подъём, тишина, рядом нужное, связь…): длина = значение, насыщенность = уверенность. SVG-компонент `Fingerprint.jsx`, используется в карточке, в списке (маленький) и в сравнении.
2. **Сравнение 2–4 отелей:** «Сравнить» в карточке → корзинка внизу экрана → экран сравнения: отпечатки рядом + таблица только по включённым линзам, победитель строки подсвечен; «чем выигрывает каждый» словами.
3. **«Было / стало»** (ответ эксперту «повлияет ли на решение»): переключатель над выдачей «Обычный поиск / С О!кном». «Обычный» — сортировка как на сайте (рейтинг, цена, «до моря по прямой»). Для отелей, которые в обычной выдаче выше, а у нас ниже, — пометка-подвох: «800 м до моря, но обратно 15 мин в гору», «вид на море только с 8-го этажа». Счётчик сверху: «Мы убрали 3 отеля, где вы бы разочаровались».
**Готово, когда.** Сравнение Pullman / Azimut / «Чайка» понятно без объяснений; «было/стало» на запросе «тихо, вид на море, близко к пляжу» показывает ≥3 подвоха; метрика «в N% запросов меняется топ-3» — в README.

## Бриф 11. «Так и было?» после поездки (`features/promise/`)
**Что.** При брони (бриф 8) сохраняем «обещание» — 3–5 фактов, которые гость видел и которые повлияли на выбор. После поездки (в демо — кнопка «Поездка завершена») — экран из 3 тапов: «Вид на море с 8-го этажа — так и было? Да / Нет / Не проверял».
**Что делает ответ.** Пишет факт-наблюдение `source: guest_feedback`; уверенность исходного факта пересчитывается (байесовски: ±0,05…0,15 в зависимости от числа ответов); «Нет» по факту отеля → вопрос отельеру; накопленные ответы → метрика калибровки «из 100 подтверждений 87 „так и было“» (имитируем 50–100 ответов для демо, помечая как демо).
**В интерфейсе.** Плашка «Как прошла поездка в Pullman?» на главной после демо-брони; в карточке у факта — «12 гостей подтвердили».
**Готово, когда.** Цикл «бронь → обещание → ответ → уверенность факта изменилась → видно в карточке» работает на одном отеле.
